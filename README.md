# Remagine

Ask one question, get answers from 8 labeled "AI" cards (Perplexity, ChatGPT,
Gemini, Claude, Grok, Copilot, Kimi, Meta AI) plus a synthesized summary.
All 8 answers and the summary are actually generated by **a single Groq API
request** to **one model** — the prompt asks the model to role-play all 8
personas and write the summary in one JSON response. This is a labeling/UX
layer, not 8 separate AI integrations, and it uses ~1 request per question
instead of 9 (see "Why one request" below).

## Project structure (kept intentionally small)

```
remagine/
├── server.js           # entire backend: Express app + Groq calls + in-memory history
├── package.json
├── .env.example         # copy to .env locally; on Render use the dashboard instead
└── public/
    ├── index.html        # your landing page (ask form now calls the real API)
    ├── chat.html          # separate page: one question, 8 answers, summary
    └── history.html       # separate page: list of all past chats
```

That's the whole app — one backend file, three static pages, no build step,
no database. `npm install && npm start` runs it.

## How it works

1. User types a question on `/` and hits **Ask**.
2. Browser calls `POST /api/ask` with the question (and which model-cards are toggled on).
3. Server sends **one** request to Groq's `/chat/completions` endpoint. The
   prompt lists all 8 personas (name + writing style) and asks the model to
   return a single JSON object: one answer per persona, plus a summary
   comparing them. JSON mode (`response_format: json_object`) keeps the
   output parseable.
4. Server parses that JSON, stores the question + 8 answers + summary in
   memory under a random ID, and returns that ID.
5. Browser redirects to `/chat.html?id=<id>`, which fetches `GET /api/session/:id`
   and renders the dedicated results page.
6. `/history.html` calls `GET /api/history` to list every question asked on
   this running server instance, newest first, each linking back to its chat page.

### Why one request instead of 8+1

The original approach called Groq once per persona (8 calls) plus once more
to summarize (9 total). That's easy to hit **rate limits** on quickly, since
Groq's free tier caps requests-per-minute and requests-per-day, not just
tokens. Asking for everything in one JSON-mode call cuts that to 1 request
per question.

**What this does and doesn't save:** it mainly protects your RPM/RPD budget.
It does *not* dramatically cut token usage — the model still has to generate
roughly the same total amount of text (8 short answers + a summary), so
input/output token costs are similar either way. If you're on a paid Groq
plan billed by tokens rather than blocked by request limits, the token bill
is about the same as before.

**Trade-off:** the 8 answers are generated by one call "acting out" 8
personas rather than 8 independent calls each fully committing to a style,
so expect slightly less distinct voices than the multi-call version. The
prompt explicitly asks the model to vary tone/angle across personas to
compensate. If a call fails entirely or returns unparseable JSON, all 8
cards fall back to a "couldn't answer" message together (since it's one
shared call) rather than failing independently per card.

**Note on history persistence:** history is stored in memory (`Map`), so it
resets whenever the server restarts or redeploys, and won't be shared across
multiple instances if you ever scale to >1 dyno. That's fine for a demo. If
you need durable history, swap the `sessions` Map in `server.js` for a real
database (Postgres, Redis, etc.) — the API shape (`/api/ask`, `/api/session/:id`,
`/api/history`) doesn't need to change.

## Environment variables

| Variable        | Required | Default              | Notes                                                                 |
|-----------------|----------|-----------------------|------------------------------------------------------------------------|
| `GROQ_API_KEY`  | Yes      | —                     | Your Groq API key from https://console.groq.com/keys                  |
| `GROQ_MODEL`    | No       | `openai/gpt-oss-20b`  | Any current Groq chat model ID. Check console.groq.com/docs/models — Groq periodically deprecates model IDs. |
| `PORT`          | No       | `3000`                | Render sets this automatically; you don't need to set it yourself.    |

## Run locally

```bash
cd remagine
npm install
cp .env.example .env
# edit .env and paste your real GROQ_API_KEY
npm start
# visit http://localhost:3000
```

## Deploy to Render

1. **Push this folder to a GitHub repo** (Render deploys from a git repo, not
   a raw zip — unzip this locally, `git init`, commit, and push to GitHub/GitLab first).

2. **Create the service on Render:**
   - Go to https://dashboard.render.com → **New** → **Web Service**.
   - Connect your GitHub repo.
   - Render should auto-detect Node. If it asks, set:
     - **Build Command:** `npm install`
     - **Start Command:** `npm start`
     - **Environment:** Node
   - Choose the Free or a paid instance type — either works for this app.

3. **Add the environment variable:**
   - In the new service, go to **Environment** (left sidebar).
   - Click **Add Environment Variable**.
   - Key: `GROQ_API_KEY`
   - Value: your real Groq key (starts with `gsk_...`)
   - (Optional) also add `GROQ_MODEL` if you want to pin a specific model.
   - Save — Render will redeploy automatically.

4. **Deploy:** Render builds and starts the service. Once live, your URL
   (something like `https://remagine.onrender.com`) serves the landing page,
   and `/chat.html` / `/history.html` work off the same deployment — no
   separate hosting needed.

5. **Verify:** open the URL, ask a question, confirm it redirects to a
   `/chat.html?id=...` page with 8 answers + a summary, and that
   `/history.html` lists it afterward.

### Notes / gotchas

- **Rotate your key.** You shared your Groq API key in this chat — treat it
  as compromised and generate a new one at https://console.groq.com/keys
  before deploying, then use the new one in Render's environment settings.
- **Free tier rate limits:** Groq's free tier has per-model request/token
  limits (see console.groq.com/docs/rate-limits). Each question now costs
  1 request, but the response is longer (8 answers + summary in one
  completion), so you can still hit token-per-minute limits under heavy
  traffic — just far less easily than with 9 separate requests. For higher
  volume, add billing on the Groq account or introduce request queuing/caching.
- **Model deprecation:** Groq periodically retires model IDs. If you start
  seeing errors, check console.groq.com/docs/models and update `GROQ_MODEL`
  in Render's environment tab.
